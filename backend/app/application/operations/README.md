# Единая архитектура операций

Статус: механизм подключён к `Service` и включён по умолчанию через
`UNIFIED_OPERATIONS_ENABLED=1`. Новые команды проходят через LLM interpreter,
coordinator и PostgreSQL-адаптеры в одной транзакции. Старый путь обслуживает
только уже существующий legacy-черновик до его завершения или истечения TTL.

## Поток данных

```text
Service: session lock → replay request_id → одна SQL-транзакция
    ↓
IntentInterpreter → Interpretation (недоверенное предложение LLM)
    ↓
OperationCoordinator: NEW / CONTINUE / CONFIRM / ABANDON
    ├─ TargetResolver: owner scope + фильтры + точный выбранный ID
    ├─ ChangePlanner: snapshot + patch → полный before/after + fingerprint
    ├─ OperationPolicy: смысл действия + обязательные поля + время + confirmation
    └─ READY → OperationExecutor → ExecutionResult
    ↓
Service: pending/history/request response → commit
    ↓
OutcomePresenter → серверные факты для HTTP/UI
```

Реализованные части:

- `domain/operations.py` — строгие модели intent, patch, snapshots, plan, pending и outcome;
- `state.py` — слияние уточнений с различением пропуска, `null`, явно неизвестного
  значения и последующего конкретного ответа;
- `coordinator.py` — таблица переходов, TTL, выбор кандидата, повторная сборка плана и ровно один executor;
- `planner.py` — стандартное слияние нескольких полей и разбор относительных дат/времени;
- `policy.py` — правила типов, запрет прошлой отмены, разделение read/update/cancel и подтверждения;
- `codec.py` — версионированный JSON состояния с обязательным `schema_version=1`;
- `presenter.py` — шаблонные вопросы, ошибки и результаты только из серверных данных;
- `ports.py` — границы LLM, поиска, SQL-исполнения и представления.

Инфраструктурные адаптеры находятся в `assistant/operation_interpreter.py` и
`storage/operation_adapters.py`; состояние добавлено миграцией
`004_unified_operations.sql`.

## Инварианты

`OperationIntent.action` различает `create`, `update`, `cancel` и `read`. Перенос
даты/времени — это `update`; одно изменение может также менять текст, тип, пояс и
длительность. Изменение сохраняет `id`, отмена меняет статус той же записи и не
реализуется через delete/create.

`TargetQuery` всегда описывает существующую запись, а `RecordPatch` — новое
состояние. Например, в «перенеси встречу с завтра на пятницу» завтра относится
к target, пятница — к patch. Resolver обязан фильтровать по `owner_id`. UUID от
модели принимается только как выбор из `candidate_ids`, ранее сохранённых сервером.

Неуказанное поле patch сохраняется; явный `null` просит очистить его.
`OperationIntent.unknown_fields` означает, что пользователь явно не знает значение;
это состояние обрабатывается общей policy для любого поля. Для длительности встречи
разрешена внутренняя оценка, обязательные дата/время/тип/текст требуют конкретного
ответа. Новый конкретный ответ снимает старую отметку `unknown`. `state.py` сливает
только `model_fields_set`, а `codec.py` сериализует с `exclude_unset=True`.
За счёт этого после JSON round-trip пропуск не превращается в очистку. Старый
creation-draft без `schema_version=1` явно отклоняется и не угадывается как новая схема.

Валидный JSON первичного LLM-разбора ещё не считается гарантированно полным. Если
в реплике есть признаки пропущенного поля, interpreter запускает source-grounded
аудит. Каждое добавление содержит точную цитату `evidence`, которую сервер проверяет
в исходном сообщении; существующее значение аудит не заменяет. Если одна цитата
допускает несколько ролей, они сохраняются в `ambiguous_fields`, а policy требует
уточнение до планирования или исполнения операции.
Для коллизии `time_expression`/`duration` действует серверная граница: конструкция
`на N часов` без ожидаемого поля, части суток или явного признака длительности
остаётся неоднозначной независимо от выбора модели.
В pending вместе с ролями сохраняются `ambiguity_values` и `ambiguity_evidence`.
Следующая реплика выбирает роль через `resolved_ambiguity`, после чего state machine
использует уже проверенное исходное значение и очищает альтернативные роли.
Тот же контракт применяется к типу записи: LLM interpreter и аудит могут отметить
`kind` неоднозначным для намерения без явного типа, policy спрашивает «Это встреча
или напоминание?», а конкретный ответ следующего хода снимает неоднозначность.

Planner формирует полный `before/after`, а `make_change_plan` считает SHA-256 по
действию, исходному revision и итоговому состоянию. При подтверждении coordinator
снова получает запись и перестраивает план. Если revision или поля изменились,
старое «да» не исполняется: пользователю показывается новый план подтверждения.
При создании ID, уже выделенный для предложенного плана, сохраняется между шагами.

`DurationInput` содержит только сказанное пользователем: `exact`, `approximate`,
`range` или `qualitative`, включая исходное `evidence`. `RecordSnapshot.user_duration`
хранит этот факт отдельно от технического `duration.minutes`. Planner использует
верхнюю границу range и server default для qualitative/отсутствующего значения;
`blocking_source` объясняет каждое решение. Плановая оценка не становится
фактической длительностью после наступления даты. Presenter показывает пользовательскую
точность и отдельно сообщает технический резерв, когда точного значения нет.
Импортированная запись сохраняет `kind=None`, пока тип явно не определён.

`duration_status` независимо хранит состояние диалога: `missing` требует вопроса,
`provided` означает пользовательское значение, `declined_to_specify` фиксирует
явный отказ уточнять, `defaulted` используется для уже финализированных legacy/default
записей. Наличие технических минут никогда само по себе не закрывает вопрос.
После уточнения planner перестраивает blocking interval, а calendar policy повторно
проверяет конфликты до выполнения операции.

## Переходы состояния

| Реплика | Допустимое действие |
|---|---|
| `NEW` | начинает новую операцию и заменяет старый pending |
| `CONTINUE` | дополняет intent; смена action отклоняется как новая команда |
| выбор UUID | разрешён только из ранее показанного списка кандидатов |
| `CONFIRM` | разрешён только для `NEED_CONFIRMATION` и того же fingerprint |
| `ABANDON` / `REJECT` | удаляет pending, но не отменяет сохранённую запись |
| истёкший TTL | отклоняется шаблонным `operation_expired` |

Если при `NEED_CONFIRMATION` пользователь отклоняет предложенный календарный слот
и просит другой вариант, LLM возвращает отдельный сигнал `alternative_requested`.
Это не новая операция и не изменение полей записи: calendar policy ищет следующее
свободное время, перестраивает план и снова ожидает подтверждения. Поэтому фразы
вроде «мне неудобно в пять, какое ещё время есть?» не зависят от словаря команд и
не могут случайно стать новым названием, чтением расписания или изменением записи.

`READ` может возвращать прошлые и будущие записи и никогда не вызывает executor.
Если запрошено конкретное поле и найдено несколько записей, coordinator сохраняет
кандидатов и просит выбрать одну, вместо угадывания.
`UPDATE` без patch, `READ` с patch и `CANCEL` с изменениями полей отвергаются.
Прошлую запись можно читать, но нельзя отменять. Встреча требует текст, дату и
время; если пользователь не назвал длительность, planner создаёт отдельный
технический default. Напоминание требует текст, дату и время; задача — текст.

Policy по умолчанию требует подтверждение для update/cancel. SQL-executor всё равно
должен повторно проверить owner, revision и пересечения непосредственно перед
UPDATE в той же транзакции. Ошибка исполнителя не перехватывается coordinator:
вся реплика откатывается, а `request_id` остаётся единственной границей replay.

## Интеграция с продуктом

- `Service` блокирует строку сессии, проверяет replay `request_id`, загружает v1
  через codec и сохраняет outcome до commit;
- resolver выполняет owner-scoped exact/substring/FTS; при пустом результате может
  применить embeddings и constrained LLM reranking только к реальным кандидатам;
- `operation_search_traces` сохраняет raw text, структурированный intent, query,
  этап поиска и ID кандидатов для диагностики;
- executor использует тот же connection, проверяет `records.version` и возвращает
  фактическую строку `RETURNING *`;
- календарная policy исключает изменяемую встречу из её собственной проверки и
  предлагает ближайший свободный слот как воспроизводимые intent + plan;
- `DefaultOutcomePresenter` сообщает только серверные факты, а внутренние оценки
  длительности не выдаёт за точные или фактические;
- `UNIFIED_OPERATIONS_ENABLED=0` оставлен как аварийный переключатель запуска.

Нельзя направлять одну реплику одновременно в новый и старый executor. Текущая
маршрутизация допускает legacy-путь только при непустом старом `sessions.pending`
и пустом `operation_state`.
