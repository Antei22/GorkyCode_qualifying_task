# GorkyCode — голосовой ассистент задач и встреч. Ссылка на готовое решение на сайте: https://95.174.93.114.nip.io/

GorkyCode — веб-приложение для управления задачами, встречами и напоминаниями на естественном русском языке. Пользователь может писать или диктовать команды, а ассистент интерпретирует запрос, при необходимости задаёт уточняющие вопросы и сохраняет результат в PostgreSQL.

Проект выполнен как тестовое задание. Основной акцент сделан не только на работе с LLM, но и на безопасном выполнении операций: модель интерпретирует пользовательский запрос, а проверка, поиск записей, изменение данных и подтверждение операций выполняются серверной логикой.

## Возможности

- создание задач, встреч и напоминаний из естественного языка;
- просмотр записей и расписания за период;
- поиск по сохранённым записям;
- изменение и отмена существующих записей;
- уточняющий диалог, если в запросе не хватает данных или фраза неоднозначна;
- работа с относительными датами: «завтра», «на следующей неделе», «до конца недели» и т. п.;
- обработка длительности встреч, включая приблизительные значения и диапазоны;
- проверка пересечений встреч и предложение ближайшего свободного времени;
- текстовый и голосовой ввод;
- озвучивание ответов средствами браузера;
- импорт демонстрационного CSV-датасета;
- гибридный поиск: PostgreSQL + embeddings + ограниченный LLM-reranking;
- хранение истории диалога и состояния незавершённой операции в PostgreSQL.

## Запуск проекта

### Требования

Для запуска достаточно установить:

- Docker Desktop / Docker Engine;
- Docker Compose v2.

Node.js, Python и PostgreSQL отдельно устанавливать не требуется — они запускаются внутри контейнеров.

### Если требуется заменить датасет, то нужно заменить .csv файл на новый

### 1. Клонировать репозиторий

```bash
git clone https://github.com/Antei22/GorkyCode_qualifying_task.git
cd GorkyCode_qualifying_task
```

### 2. Создать `.env`

Файл `.env` нужно создать в корне репозитория и заполнить следующими данными:

```dotenv
APP_TIMEZONE=Europe/Moscow
# Empty = real clock. Fixed ISO timestamp is only for reproducible demos/tests.
APP_FIXED_NOW=
FRONTEND_PORT=8080
POSTGRES_USER=gorky
POSTGRES_PASSWORD=gorky-local-only
POSTGRES_DB=gorky
# Host development only; Docker overrides this with db:5432.
DATABASE_URL=postgresql://gorky:gorky-local-only@localhost:5434/gorky
# OpenAI-compatible provider, e.g. your separately running gpt2giga.
# host.docker.internal reaches a host service from Docker Desktop.
LLM_BASE_URL=https://openrouter.ai/api/v1
LLM_API_KEY=сюда нужно вставить ключ, доступный по ссылке https://disk.360.yandex.ru/i/I5vIJrU1ERQQwA (сразу после = без пробелов)
LLM_MODEL=google/gemma-4-26b-a4b-it
LLM_TIMEOUT_SECONDS=60
# Optional bundled proxy: set LLM_BASE_URL=http://gpt2giga:8090/v1,
# supply your own keys, then start with --profile gigachat.
GIGACHAT_CREDENTIALS=
GIGACHAT_SCOPE=GIGACHAT_API_PERS
FRONTEND_ORIGIN=http://localhost:8080
COOKIE_SECURE=0
```

Без настроенной модели интерфейс и база данных запустятся, но обработка команд ассистентом работать не будет.

### 3. Запустить приложение

```bash
docker compose up -d --build
```

Проверить состояние контейнеров:

```bash
docker compose ps
```

После запуска доступны:

| Компонент | Адрес |
|---|---|
| Web UI | http://localhost:8080 |
| Swagger / API | http://localhost:8010/docs |
| Health check | http://localhost:8010/api/health |
| PostgreSQL с хоста | `127.0.0.1:5434` |

Логи backend:

```bash
docker compose logs -f backend
```

Остановить приложение:

```bash
docker compose down
```

Данные PostgreSQL сохраняются в Docker volume. Чтобы полностью удалить локальные данные:

```bash
docker compose down -v
```

## Архитектура

```text
┌────────────────────────────┐
│ React + TypeScript frontend│
│ текст / голос / TTS        │
└──────────────┬─────────────┘
               │ HTTP / JSON
               ▼
┌────────────────────────────┐
│ nginx                      │
│ UI + proxy /api            │
└──────────────┬─────────────┘
               ▼
┌────────────────────────────┐
│ FastAPI backend            │
│                            │
│ LLM interpreter            │
│        ↓                   │
│ operation coordinator      │
│        ↓                   │
│ resolver / planner / policy│
│        ↓                   │
│ repository                 │
└──────────────┬─────────────┘
               ▼
┌────────────────────────────┐
│ PostgreSQL 16              │
│ записи / сессии / история  │
└────────────────────────────┘
```

LLM не получает прямого доступа к базе данных и не выполняет операции самостоятельно. Она возвращает структурированное описание намерения пользователя, после чего backend самостоятельно:

1. валидирует результат;
2. определяет целевую запись;
3. проверяет обязательные поля и неоднозначности;
4. строит план изменения;
5. проверяет бизнес-правила;
6. только после этого изменяет PostgreSQL.

Такой подход уменьшает риск того, что модель придумает идентификатор записи, некорректно изменит данные или выполнит операцию, которую пользователь не запрашивал.

## Самостоятельно принятые решения

При реализации проекта были дополнительно приняты следующие решения.

**1. LLM используется как интерпретатор, а не как исполнитель.**  
Модель формирует структурированный intent, но не получает прямого mutation-доступа к БД. Все изменения проходят через серверный coordinator и policy layer.

**2. Создание, чтение, изменение и отмена сведены к единому механизму операций.**  
Вместо отдельных независимых сценариев используется state machine с единым состоянием незавершённой операции. Это позволяет одинаково обрабатывать уточнения, исправления и подтверждения.

**3. Неоднозначные команды не угадываются молча.**  
Например, фраза вроде «на 4 часа» в зависимости от контекста может означать время начала или длительность. Если контекста недостаточно, ассистент должен запросить уточнение.

**4. Длительность пользователя отделена от технического резервирования календаря.**  
Фраза «час-два» сохраняется как диапазон 60–120 минут, а для проверки пересечений календарь может резервировать верхнюю границу диапазона.

**5. Поиск существующих записей ограничен реальными объектами из PostgreSQL.**  
LLM может ранжировать только кандидатов, найденных сервером, и не может самостоятельно придумать ID записи.

**6. Добавлена защита от повторного выполнения запроса.**  
Запросы используют `request_id`, а операции выполняются транзакционно. Повторная отправка одного запроса не должна создавать дубликаты.

**7. Импорт тестового датасета сделан идемпотентным.**  
Повторная загрузка CSV не создаёт дубли уже импортированных строк.

## Что можно улучшить при наличии дополнительного времени

- добавить полноценную регистрацию и авторизацию вместо временной cookie-сессии;
- подключить внешние календари, например Google Calendar / Яндекс Календарь;
- добавить production-ready server-side Speech-to-Text как fallback для браузерного распознавания;
- расширить end-to-end тесты диалогов и сценариев с реальной LLM;
- добавить observability: структурированные логи, метрики, tracing и мониторинг ошибок;
- добавить CI/CD с автоматическим запуском backend/frontend тестов и сборкой Docker-образов;
- улучшить работу семантического поиска на большом количестве пользовательских записей;
- добавить полноценную пользовательскую модель, роли и синхронизацию данных между устройствами.
