# GorkyCode — голосовой ассистент задач и встреч

GorkyCode — прототип голосового ассистента для управления личными задачами,
встречами и напоминаниями на естественном русском языке. Приложение принимает
текст и голос, хранит записи в PostgreSQL, поддерживает уточняющий диалог,
просмотр расписания и поиск по истории.

Дата состояния: 28.10.2026. Это уже код приложения, а не только план.
Подключение к реальной LLM и ручная проверка микрофона остаются отдельными
интеграционными шагами; ниже явно указано, что проверено.

## Быстрый запуск

Требуется Docker Desktop с Linux containers. Все команды выполняются из корня
клонированного репозитория `GorkyCode_qualifying_task`:

```powershell
docker compose up -d --build
docker compose ps
```

Открыть **http://localhost:8080**. Сразу доступны загрузка 1000 примеров,
список и поиск. Без ключа модели чат покажет сообщение о настройке LLM;
ответы модели не подменяются моками. Данные примеров загружаются только
кнопкой «Загрузить 1000 примеров», а не автоматически при открытии.

```powershell
docker compose logs -f backend
docker compose down
```

Остановка не удаляет данные. Compose project называется `gorkycode`, данные
хранятся в volume `gorkycode_gorky_data`, сессия — в cookie `gorkycode_session`.

Адреса для локальной разработки:

| Компонент | Адрес |
|---|---|
| UI через nginx | http://localhost:8080 |
| API / Swagger | http://localhost:8010/docs |
| API health | http://localhost:8010/api/health |
| PostgreSQL с хоста | 127.0.0.1:5434 |
| PostgreSQL из контейнера backend | db:5432 |

Порты опубликованы только на loopback. Настройки подключения локальной БД по
умолчанию находятся в `.env.example`; это демонстрационные значения.

## Подключение модели

Скопировать шаблон `.env.example` в `.env` и заполнить собственные настройки.
Файл `.env`, ключи и сертификаты не добавлять в репозиторий.

### Вариант 1: любой доступный OpenAI-совместимый endpoint

Задать `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`. Провайдер должен
поддерживать tool calling. Для сервиса на хосте Docker Desktop используется
`host.docker.internal`, а не `localhost` внутри контейнера.

```dotenv
LLM_BASE_URL=http://host.docker.internal:8090/v1
LLM_API_KEY=your-provider-key
LLM_MODEL=GigaChat-3-Lightning
```

Это пример адреса. Он предполагает, что совместимый прокси уже запущен на
хост-машине на порту 8090.

После настройки:

```powershell
docker compose up -d --build
```

### Вариант 2: отдельный gpt2giga внутри GorkyCode

В репозитории есть опциональный Dockerfile прокси. Он запускается только профилем
`gigachat`; ключи и сертификаты пользователь предоставляет через локальное окружение.

```dotenv
LLM_BASE_URL=http://gpt2giga:8090/v1
LLM_API_KEY=your-own-proxy-secret
LLM_MODEL=GigaChat-3-Lightning
GIGACHAT_CREDENTIALS=your-gigachat-credentials
GIGACHAT_SCOPE=GIGACHAT_API_PERS
```

`LLM_API_KEY` здесь — самостоятельно выбранный ключ защиты прокси,
`GIGACHAT_CREDENTIALS` — учётные данные GigaChat: это разные значения.

```powershell
docker compose --profile gigachat up -d --build
docker compose logs -f gpt2giga backend
```

Если для GigaChat в вашей среде нужен дополнительный доверенный CA, подключить
собственный bundle в контейнер прокси и настроить
`GIGACHAT_CA_BUNDLE_FILE` через локальный compose override.
Проверка TLS не отключена. Реальный доступ к модели/CA требует проверки
на окружении владельца; профиль прокси в этой итерации не запускался.

## Что реализовано

- Четыре единых действия над task/meeting/reminder: создание, чтение, изменение
  нескольких полей и отмена. Просмотр периода и поиск истории используют тот же read.
- LLM делает один структурированный вызов `propose_operation` и не получает
  инструментов записи. Переходы, уточнения и выполнение контролирует coordinator.
- Явная проверка входных полей, вычисление основных относительных дат кодом.
- Русские значения типа от LLM (`встреча/встречу`, `задача/задачу`,
  `напоминание`) нормализуются в `meeting/task/reminder`; технические ошибки
  Pydantic не показываются пользователю.
- Серверный многошаговый черновик уточнения и история диалога в PostgreSQL.
  Backend выбирает одно недостающее поле и формирует проверяемый шаблонный вопрос,
  а черновик автоматически очищается через 30 минут бездействия.
- Отмена сообщает тип удалённого черновика; если черновика нет, приложение
  прямо сообщает, что отменять нечего.
- Пользовательская длительность отделена от технического резервирования календаря.
  `user_duration` сохраняет точное, приблизительное, диапазонное или качественное
  высказывание вместе с `evidence`; `blocking_duration_minutes` и
  `blocking_duration_source` отвечают только за занятый интервал. Для `час-два`
  хранится диапазон 60–120 минут, а календарь безопасно блокируется на 120 минут.
  Если длительность не названа, planner сразу рассчитывает предварительный default,
  но `duration_status=missing` заставляет policy спросить пользователя. Ответ
  «не знаю» переводит статус в `declined_to_specify`, после чего встреча создаётся
  с default без повторного вопроса и без выдачи его за слова пользователя.
- Пересечения встреч по интервалам проверяются, включая старые встречи без
  длительности (для них принято 60 минут). При конфликте backend предлагает
  ближайший свободный слот в будни с 09:00 до 18:00 в пределах 30 дней и ждёт
  подтверждения; ответ «да» сохраняет в предложенный слот, перенос текущих встреч
  автоматически не выполняется.
- Неоднозначное «хочу созвониться/позвонить/встретиться» сначала требует выбрать встречу или
  напоминание. Для встречи уже названное время относится к событию; для напоминания
  исходная фраза становится текстом, а время срабатывания запрашивается отдельно.
- Явная команда «отмени/удали встречу, задачу или напоминание» использует тип записи
  как фильтр. Результаты упорядочены по времени: сначала ближайшие предстоящие,
  затем записи без даты и прошедшие — от недавних к старым. Историю можно искать
  и просматривать, но отменять уже прошедшие записи нельзя.
- Отмена разрешена только явной командой в текущей реплике. Ошибочный вызов
  `cancel_record` моделью на вопрос или просьбу изменить длительность отвергается сервером.
- `update_meeting_duration` меняет существующую будущую встречу на месте. «Будет длиться
  долго» сохраняется как качественное описание с оценкой для проверки пересечений;
  числовая длительность не выдумывается как точный факт. Увеличение интервала сообщает
  о новых пересечениях, если они появились. Неоднозначная встреча требует уточнения.
- `get_meeting_duration` учитывает время запроса: «будет длиться» ищет предстоящие
  встречи, «длилась» — прошедшие, конкретная дата сужает поиск до этого дня.
  Импортированные названия встреч доступны для чтения без присвоения им типа;
  связанные задачи «Отправить итоги встречи» в эту выдачу не входят.
- `blocking_duration_source` различает `user_exact`, `user_approximate`,
  `user_range_max`, `qualitative_default`, `event_type_default` и
  `legacy_unknown`. Старые `duration_*` остаются совместимыми aliases API.
  Для истории различаются записанный план и фактическая продолжительность:
  измерение фактического времени не реализовано.
- Транзакция на реплику: при сбое модели после создания запись откатывается.
- Идемпотентность по `request_id`; повтор того же текста с тем же id возвращает
  прежний результат, другой текст с тем же id отвергается.
- Изоляция записей по случайной cookie-сессии, блокировка конкурирующих реплик
  одной сессии. Это ещё не полноценная авторизация нескольких пользователей.
- CSV-импорт без LLM, транзакционно и без повторов по идентификатору источника.
- Гибридный поиск: exact/substring/русский PostgreSQL FTS, затем embeddings fallback
  и ограниченный LLM reranking только среди реальных строк БД. Неуверенный выбор
  приводит к уточнению, а не к придуманному ID. Каждый operation-поиск сохраняет
  raw text, структурированный intent, итоговый query, этап и ID кандидатов.
- React UI: чат, источники, список, поиск, импорт и редактируемая расшифровка.
- Браузерные STT/TTS для русского языка с текстовым вводом при недоступности голоса.
- Docker Compose, миграции и все исходники находятся в одном самостоятельном репозитории.

Ассистент выполняет локальное создание сразу после получения достаточных полей.
Окно подтверждения перед каждой записью не используется. Подтверждение создания
формируется сервером по сохранённым данным; отправляется после commit.
Для списка и поиска LLM оформляет только результат соответствующего инструмента;
фактические записи в API всегда берутся из SQL. Системные подтверждения создания,
отмена, истечение/отсутствие черновика и ошибки остаются серверными шаблонами.
Если модель вернула пустой текст, список, поиск или уточнение имеют шаблонный fallback.
Реальные календари и почта не подключены.

## Архитектура

### Единый механизм операций

В `backend/app/domain/operations.py` и `backend/app/application/operations/`
реализованы и подключены строгие контракты, state machine, LLM interpreter,
PostgreSQL resolver/executor, общий planner, календарная policy, versioned codec
состояния и шаблонный presenter. Создание, изменение сразу нескольких полей,
перенос, отмена и чтение проходят одним механизмом переходов.
Подтверждение привязано к fingerprint и revision; произвольный UUID от модели
не даёт доступа к записи, а устаревший план перед исполнением строится заново.

Состояние хранится отдельно в `sessions.operation_state`, записи имеют optimistic
`version`. Старый tool-loop используется только для завершения legacy-черновика,
который существовал до миграции; новые реплики не проходят через два исполнителя.
Подробности описаны в [архитектуре операций](backend/app/application/operations/README.md).
Проверен 121 backend-сценарий: автономный прогон и PostgreSQL-регрессии на
отдельной БД `gorky_regression`; frontend build/lint также проходят. Реальный
semantic fallback зависит от поддержки `/embeddings` настроенным провайдером.

### Действующий путь запроса

```text
frontend/
  текст или браузерный STT → редактируемый текст
                       ↓
backend/app/main.py — HTTP, cookie, входные модели, ошибки
                       ↓
service.py — session lock, replay request_id, одна транзакция
                       ↓
assistant/operation_interpreter.py — только структурированный intent
                       ↓
application/operations/ — coordinator → resolver → planner → policy
                       ↓
storage/operation_adapters.py — optimistic executor
                       ↓
                   PostgreSQL

data/*.csv → ingestion/ → тот же репозиторий
Ответ API → текст UI → опциональный браузерный TTS
```

LLM не исполняет SQL и не получает mutation-tools. Единственный структурированный
вызов `propose_operation` возвращает недоверенное предложение `action/target/changes`.
Coordinator сам выбирает недостающее поле, ограничивает выбор ранее показанными
кандидатами, строит полный before/after и исполняет только серверный `READY`.
Ожидаемое поле передаётся модели как часть контекста: поэтому разговорное
«на 4 дня» после вопроса о времени трактуется как `16:00`, тогда как в другом
контексте та же последовательность слов может иметь иной смысл.
Уточнения сохраняются в `PendingOperation`; явный `null` отличается от пропуска,
а `unknown_fields` означает, что пользователь явно не знает значение. Конкретный
ответ следующего хода всегда снимает старую отметку `unknown`.
При признаках пропущенного значения запускается второй source-grounded аудит LLM.
Добавить поле он может только вместе с точной цитатой `evidence` из текущей реплики;
сервер проверяет цитату и не разрешает аудиту перезаписывать уже извлечённое значение.
Неоднозначные выражения сохраняются в `ambiguous_fields` и блокируют выполнение до
уточнения: `в 16:30` однозначно восстанавливает время, а `на 4 часа` без контекста
требует выбрать время начала или длительность, даже если LLM сама выбрала одну роль.
Фразы `длительностью на 4 часа` и `на 4 часа дня` содержат достаточный контекст и
трактуются соответственно как длительность и время начала `16:00`.
Pending хранит исходную цитату и допустимые значения неоднозначного выражения, поэтому
ответа `длительность` или `время начала` достаточно: повторять `4 часа` не требуется.
Неоднозначность типа также передаётся структурированно: намерения вроде «хочу
увидеться/встретиться/созвониться» без явно названного типа сначала приводят к
вопросу «Это встреча или напоминание?». Синонимы определяет LLM-аудит, а не словарь
команд в серверном коде.
«Отмена» очищает операцию, но не отменяет сохранённую запись. Update/cancel требуют
подтверждения, связанного с fingerprint и текущей версией записи.

Основная запись: `id`, `owner_id`, `kind`, `text`,
`scheduled_date`, `scheduled_time`, `user_duration`, `duration_status`, `duration_minutes`,
`blocking_duration_source`, совместимые `duration_source`/`duration_description`,
`timezone`, `created_at`,
`updated_at`, `status`, `source`, `source_id`, `raw_payload`.
Время/дата nullable для задач без срока, `kind` nullable для неразмеченного импорта.
Миграции применяются автоматически при старте API, под advisory lock.

Хранилище интерфейса не является источником истины: история и ожидающий
черновик переживают перезапуск backend. Потеря cookie или другой браузер создаёт
отдельную пустую сессию, а не открывает прежние данные.

## Технологии и ключевые решения

| Область | Решение |
|---|---|
| Backend | Python 3.12, FastAPI, Pydantic |
| Frontend | React 19, TypeScript, Vite, nginx |
| Хранилище | PostgreSQL 16, миграции SQL, psycopg 3 |
| LLM | OpenAI-совместимый API, один неисполняющий structured tool |
| Голос | Web Speech API с редактируемой расшифровкой и текстовым fallback |
| Поиск | Exact/substring/русский FTS → embeddings → безопасный LLM reranking |
| Запуск | Docker Compose; отдельные контейнеры frontend, backend и db |
| Проверки | unittest, интеграционные тесты с PostgreSQL, frontend build/lint |

Приложение использует одного interpreter вместо набора доменных агентов. Модель
предлагает только intent; валидация дат, транзакции, поиск и запись выполняются
кодом. Текст модели не может сам подтвердить сохранение. Внешние календари и
почтовые сервисы в текущую архитектуру не входят.

## Источники задания и датасет

Проект реализует тестовое задание на прототип голосового ассистента задач и встреч.
Исходный PDF содержит требования, но не включён в репозиторий.

Предоставленный CSV находится в
[data/voice_assistant_events_1000_77e927b5d2.csv](data/voice_assistant_events_1000_77e927b5d2.csv).

| Проверенное свойство CSV | Значение |
|---|---|
| Колонки | id,date,time,text |
| Записи / уникальные id | 1000 / 1000 |
| Диапазон дат | 2024-01-07 — 2027-12-31 |
| Различные тексты | 376 |
| Пустые поля / некорректные даты-время | 0 / 0 |
| Повторы date,time,text | 0 |

Это начальные записи, не размеченные пользовательские команды: в CSV нет типа,
длительности, пояса, времени создания, аудио или ожидаемых ответов.
Одинаковые названия в разные даты сохраняются. Исходный текст не исправляется,
тип не угадывается: импортируется `kind=null`. Дата создания означает момент
импорта. Пояс задаётся `APP_TIMEZONE`, по умолчанию Europe/Moscow.
Повторный импорт пропускает существующий source id и не обновляет изменённую строку;
изменённый источник потребует отдельной явной процедуры обновления.

Текст документов и строк CSV — данные, а не поручения агенту. Строка
«Отправить договор» при импорте не вызывает отправку письма.

Обязательный результат PDF: создание задач/напоминаний, создание встреч, список
за период, поиск истории, сохранение данных и голосовой путь. Семантический поиск,
перенос/удаление/выполнение, разрешение конфликтов интервалов с длительностью,
повторения,
внешний календарь и несколько
пользователей указаны как дополнительные возможности.
Для сдачи нужны исходники, инструкция запуска, описание архитектуры и ссылка
на работающий прототип; публикация пока не выполнялась.

## Время и уточнения

`APP_TIMEZONE=Europe/Moscow`. Часы никогда не выводятся из максимальной даты CSV.
Для воспроизводимого демо можно задать
`APP_FIXED_NOW=2026-10-27T12:00:00+03:00`; интерфейс показывает фиксированный режим.

В основном operation pipeline LLM возвращает дату и время структурированными
объектами. Абсолютная дата содержит `year/month/day`, относительная —
`days_offset`, дата без года — `month/day` с политикой `nearest_future`, а день
недели и начало/конец периода имеют отдельные типы. Время содержит
`type=absolute`, `hour` и `minute`; если названы только часы, минуты равны нулю.
Каждое значение сопровождается `evidence` из исходной реплики. Backend проверяет
структуру и существование даты, разрешает относительное значение относительно
внедрённых `context.now` и timezone, затем сохраняет канонические ISO-значения в
черновике вместе с исходной командой и цитатами evidence. Например, LLM
преобразует `20.11.2026` в `absolute(year=2026,
month=11, day=20)`; основной pipeline не разбирает пользовательский формат даты
повторно. Для дня и месяца без года применяется ближайшая дата в будущем,
включая сегодня. `в пятницу` означает ближайшую пятницу; `в следующую пятницу`
— день следующей календарной недели. Текстовые date/time-параметры остаются в
legacy-инструментах чтения длительности и старых интеграционных интерфейсах.
Контракт запрещает повторно использовать число из даты в качестве минут времени:
`в 10 30.10.26` означает `10:00` и `30.10.2026`, с отдельными evidence `10` и
`30.10.26`.

Семантический контракт поддерживает абсолютные даты, сдвиг в днях, день недели,
границы недели/месяца и дату без года. Неделя — понедельник–воскресенье.
Модель не должна вычислять календарную дату для относительных выражений; это
делает backend. «На следующей неделе» без дня требует уточнения. «Вечером», «утром» и
«после обеда» без точного часа требуют времени, а не получают придуманное значение.
При создании прошедшая дата или уже прошедшее время сегодня отвергаются сервером;
просмотр и поиск прошлых записей при этом остаются доступными.
Задача «до конца недели» получает дату воскресенья без выдуманного времени.

Задачу можно сохранить без даты/времени. Встреча и напоминание требуют дату
и время; ответы могут последовательно заполнить тип, текст, дату и время.
На каждом шаге задаётся только один вопрос. Ответ «в 11» дополняет сохранённый
`PendingOperation`, если interpreter определил продолжение. Черновик живёт
30 минут с последнего изменения; после этого создание нужно начать заново.
Короткий ответ на серверный уточняющий вопрос может изменить только ожидаемое
поле и связанный с ним `unknown`/`clear`-сигнал. Например, ответ `час-два` на
вопрос о длительности не может заменить уже собранный текст встречи.
Длительность имеет отдельный структурированный контракт: `exact`, `approximate`,
`range` и `qualitative`. Диапазон и приблизительное значение не превращаются в
точный факт; server-side проверка восстанавливает тип и `evidence` из исходной
реплики. Технический интервал вычисляется planner: exact/approximate используют
названные минуты, range — верхнюю границу, qualitative и отсутствие значения —
server default. Проверка конфликтов и `reserved_until` используют только этот
технический интервал.
Один ответ может заполнить сразу несколько полей: «Позвонить Ивану завтра в 10»
сразу завершает черновик напоминания, а вариант без времени запрашивает только время.
Время поддерживает HH:MM и точные выражения вроде «в 3 дня» или «10 утра».
Произвольные сложные даты, праздники и повторения пока не реализованы:
неподдержанное выражение требует уточнения, а не угадывания.

## API

| Метод | Путь | Назначение |
|---|---|---|
| GET | /api/health | БД доступна, настроен ли ключ модели |
| GET | /api/session | Cookie-сессия, часы, настройки и ожидающий черновик |
| GET | /api/history | Последние 100 реплик текущей сессии |
| POST | /api/chat | message и UUID request_id |
| GET | /api/records | period, kind, query, date_from, date_to |
| POST | /api/import/demo | Импорт вложенного CSV в текущую сессию |

Просмотр ограничен 100 записями, поиск — 20. Поиск всегда по всей истории;
его нельзя комбинировать с периодом, отличным от all.
`period`: all, today, tomorrow, day_after_tomorrow, this_week, next_week, custom.
Для custom нужны date_from и date_to. Полной пагинации пока нет.
API-клиенты сначала вызывают /api/session и сохраняют cookie.
История для контекста LLM ограничена последними 20 репликами.

В выдаче записи одновременно доступны `user_duration`, `duration_status`,
`blocking_duration_minutes`, `blocking_duration_source` и вычисляемый
`reserved_until`. Старые `duration_minutes`, `duration_source` и
`duration_description` пока сохранены для совместимости.

LLM разделяет `target_query` (только идентифицирующая часть записи) и
`requested_fields` (что прочитать). Например, вопрос «Сколько будет длиться
встреча с мамой» ищет `встреча с мамой`, а не всю фразу. SQL сначала выполняет
exact/substring/FTS. Если результатов нет и `SEMANTIC_SEARCH_ENABLED=1`, backend
запрашивает embeddings через модель `LLM_EMBEDDING_MODEL`, ранжирует только
owner-scoped строки БД и при необходимости отдаёт эти реальные кандидаты LLM.
Ошибка или отсутствие embeddings не ломают обычный поиск. При неоднозначности
пользователь выбирает один из показанных кандидатов.

CLI для импорта своего файла в существующую сессию:

```powershell
docker compose exec backend python -m app.ingestion.csv_import /app/data/voice_assistant_events_1000_77e927b5d2.csv --owner YOUR_SESSION_UUID
```

UUID показан в UI. CLI работает от имени оператора с доступом к контейнеру;
публичный HTTP API не принимает произвольный owner.

## План работы команды из шести человек

Работу следует вести тремя парами. Каждая пара отвечает за свой вертикальный
результат, а не только за набор файлов. Внутри пары один человек ведёт основную
реализацию, второй — интеграцию и проверку пограничных сценариев. Это не означает,
что второй участник занимается только тестами: оба делают код и проверяют изменения
друг друга до передачи в общую ветку.

| Команда | Участник A | Участник B | Результат пары |
|---|---|---|---|
| 1. Ассистент и бизнес-логика | LLM, промпт и tool calling | Даты, уточнения и транзакции | Четыре обязательных действия стабильно работают с реальной моделью |
| 2. Голос и интерфейс | STT/TTS и ошибки устройств | UX чата, состояний и мобильного экрана | Полный голосовой и текстовый пользовательский путь |
| 3. Данные и выпуск | Поиск, импорт и качество данных | E2E, CI, Docker и публикация | Воспроизводимый прототип, который можно проверить по ссылке |

### Общий приоритет

Перед дополнительными функциями необходимо закрыть обязательный результат задания:

1. Подключить и проверить реальную LLM.
2. Создавать задачи/напоминания и встречи из свободной русской речи.
3. Показывать записи за период и находить старые записи.
4. Провести настоящий голосовой сценарий в выбранном браузере.
5. Запустить проект из чистой копии и опубликовать демонстрационный стенд.

Изменение, удаление, выполнение задач, повторения, конфликты ресурсов/площадок,
внешний календарь, полноценные аккаунты и фоновая доставка уведомлений относятся к этапу
после MVP. Их не следует начинать, пока обязательная приёмка нестабильна.

### Команда 3 — данные, поиск, тестирование и выпуск

Зона владения:

- `backend/app/storage/`, `backend/app/ingestion/`, миграции и API списка;
- `data/` и отдельные оценочные наборы без секретов и персональных данных;
- `backend/tests/`, будущие E2E-тесты, Docker Compose и CI;
- README, инструкция демонстрации и публикация.

Участник 3A — данные и качество поиска:

- разметить небольшой эталон: 40–60 поисковых запросов, ожидаемые CSV `id` и
  допустимые варианты релевантности; включить словоформы, имена, опечатки,
  прошлые даты и повторяющиеся названия;
- посчитать понятные метрики, например Recall@5 и MRR, сохранить способ запуска;
- настроить ранжирование FTS и substring fallback на основе измерений;
- добавлять embeddings только если лексический поиск не проходит согласованный
  порог: это отдельная миграция, воспроизводимое построение индекса и fallback;
- добавить пагинацию к `/api/records`, потому что сейчас список ограничен 100,
  а поиск — 20 записями; согласовать контракт до изменения frontend;
- проверить импорт повреждённого CSV, повторный импорт, кодировку с BOM,
  транзакционный rollback и сохранение пользовательских записей;
- решить, нужен ли безопасный режим замены версии источника. Текущее поведение
  намеренно не обновляет строку с уже известным `source_id`.

Участник 3B — сквозная проверка и выпуск:

- добавить CI: backend unit/integration, frontend build/lint, `docker compose config`;
- подготовить E2E-smoke через браузер или HTTP для четырёх обязательных действий;
- проверить запуск из чистого clone по README без локальных неотслеживаемых файлов;
- проверить репозиторий GorkyCode и убедиться, что `.env`, ключи,
  сертификаты, volume и пользовательские данные не попали в историю;

Результат команды 3 принимается, когда:

### Контракты между командами

Чтобы три пары могли работать параллельно, до начала изменений зафиксировать:

| Контракт | Владелец | Кто согласует изменения |
|---|---|---|
| `POST /api/chat`, `GET /api/session`, формат ошибки | Команда 1 | Команды 2 и 3 |
| `GET /api/records`, пагинация и поисковая выдача | Команда 3 | Команды 1 и 2 |
| `ChatResponse`, `RecordItem`, состояния голоса | Команда 2 | Команда 1 |
| Таблицы `records`, `sessions`, `chat_*` и миграции | Команда 3 | Команда 1 |
| Значение относительных дат и правила уточнения | Команда 1 | Команды 2 и 3 |
| Команды запуска, переменные окружения и порты | Команда 3 | Все команды |

Изменение общего контракта начинается с короткого описания нового запроса и ответа,
после чего одновременно обновляются backend, frontend, тесты и README. Не передавать
между командами неописанный JSON и не использовать текст ответа модели как API-контракт.

### Ветки и интеграция

Рекомендуемая структура веток:

- `gorky/assistant` — команда 1;
- `gorky/voice-ui` — команда 2;
- `gorky/data-release` — команда 3;
- `gorky/integration` — последовательное объединение готовых изменений.

Каждая задача оформляется небольшим PR с одним проверяемым результатом. Автор не
объединяет собственный PR без просмотра вторым участником пары. Изменения общих
контрактов дополнительно смотрит представитель затронутой команды.

Порядок интеграции:

1. Команда 1 фиксирует существующий HTTP-контракт и набор обязательных диалогов.
2. Команды 2 и 3 параллельно работают с этим контрактом; команда 1 подключает LLM.
3. Сначала объединяются миграции/API данных, затем бизнес-логика, затем UI.
4. Каждая команда проводит приёмку результата другой пары по её критериям.
5. Команда 3 запускает общий CI и Docker smoke; команда 1 — реальные LLM-сценарии;
   команда 2 — ручную голосовую матрицу.
6. После исправлений создаётся release-кандидат и выполняется демонстрация из
   чистой браузерной сессии.

Не использовать общий рабочий `.env` в ветках. Миграции только добавляются новым
файлом и не переписывают уже применённую `001_initial.sql`. При конфликте в README
сохранять актуальный статус проверок, а не механически выбирать одну сторону.

### Единый parser и безопасный merge follow-up

Дата, время и пользовательская длительность извлекаются общим структурированным
LLM-контрактом для всех типов записей. В follow-up `expected_field` задаёт
обязательное поле, но parser сохраняет в patch и остальные явно указанные значения.
Backend сравнивает нормализованные значения с черновиком: пустые принимает,
совпадающие оставляет, а отличающиеся хранит отдельно в `pending_changes` до ответа
пользователя. Безопасные части того же patch при конфликте не теряются; явный
`turn=correction` применяет замену сразу. После merge planner и policy заново
вычисляют недостающие поля и проверяют календарные пересечения.

Регрессии покрывают совместный ввод даты и времени, нормализацию relative date,
семантически равные значения, подтверждение и отклонение конфликтующего времени,
сохранение безопасной даты и явную коррекцию.

Финальные образы собраны и запущены. frontend, backend и db имеют статус healthy.
UI на http://localhost:8080 и /api/health отвечают HTTP 200.
Через nginx/API проверены новая сессия, импорт 1000 строк, повторный импорт
(0 новых, 1000 пропущено), список и поиск; чат без ключа возвращает явную
ошибку настройки, не фиктивный ответ. В текущем запуске LLM_API_KEY не задан.

Контейнерный TestClient выводит предупреждение Starlette о будущем переходе
с httpx на httpx2; все проверки проходят. При обновлении тестового стека
проверить совместимость TestClient, не менять HTTP-клиент приложения вслепую.
Необязательный профиль gigachat проверен на корректность compose-конфигурации,
но сам прокси с реальными учётными данными не запускался.
